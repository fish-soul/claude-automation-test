# Figma → Claude Code 변환 방법론 테스트 결과

> **목적:** 피그마에서 만든 디자인을 Claude Code로 코드화하는 가장 좋은 방법 찾기
> **테스트 대상:** KRDS v1.0.0 (한국 정부 디자인 시스템)
> **테스트 일자:** 2026-03-24

---

## 평가 기준

| 항목 | 뜻 |
|------|----|
| **정밀도** | 피그마 원본과 얼마나 똑같이 나왔는가 |
| **속도** | 결과물이 나오기까지 얼마나 걸렸는가 |
| **준비 비용** | 디자이너가 사전에 준비해야 하는 작업량 (★이 많을수록 쉬움) |
| **재사용성** | 만들어진 코드를 실제 서비스에 바로 가져다 쓸 수 있는가 |

---

## 방법 1. 피그마 링크만 던지기 (URL + MCP)

### 한 줄 요약
> 피그마 컴포넌트 링크를 Claude에 붙여넣으면 Claude가 직접 피그마를 열어보고 코드를 짠다.

### 평가 결과

| 항목 | 점수 | 설명 |
|------|------|------|
| 정밀도 | ★★★ | 색상·폰트·상태별 스타일 등 정적인 요소는 잘 반영됨. 그러나 동적 인터랙션에서 두 가지 구현 오류 확인 (아래 이슈 참고) |
| 속도 | ★★★★★ | 링크 전달 후 수 분 이내 완성 |
| 준비 비용 | ★★★★★ | 피그마 링크 복사 외 추가 작업 없음 |
| 재사용성 | ★★★★ | 날짜 계산, 클릭 동작 등 실제 기능까지 포함된 완성 컴포넌트가 나옴 |

### 테스트 내용: KRDS 캘린더 컴포넌트 구현

**디자이너가 한 일:** 피그마 링크 4개 복사해서 전달

| 링크 종류 | 이유 |
|-----------|------|
| 컴포넌트 메인 화면 | 최종 모습 파악용 |
| 가이드/스펙 화면 | 상태별 동작 규칙 파악용 |
| 아토믹 화면 | 버튼·셀 등 작은 단위 요소 파악용 |
| 연도/월 피커 컴포넌트 | 드롭다운 팝업이 별도 컴포넌트라 따로 필요 |

**Claude가 한 일 (자동):**
- 피그마를 직접 읽어 색상값, 폰트, 간격, 상태별 스타일 추출
- 컴포넌트 스크린샷으로 시각 검증
- 실제 동작하는 캘린더 컴포넌트 코드 생성

**결과물에 포함된 기능:**
- 날짜 선택 모드 (하루 / 기간)
- 이전·다음 달 이동
- 오늘 날짜 표시 (빨간 점)
- 연도·월 드롭다운 선택
- 범위 선택 시 hover 프리뷰
- 하단 오늘 이동 / 취소 / 선택 버튼

---

### 구현 오류 기록

#### 이슈 1. 기간 선택 시 중간 날짜 배경이 끊김

**증상:**
기간(period) 모드에서 날짜 범위를 선택하면 중간 날짜들이 흰 배경으로 이어져야 하는데,
날짜 셀 사이에 틈이 생겨 배경이 불연속적으로 나타남.
예: 17일(시작)~21일(끝) 선택 시 → 19·20일 주변에 여백 발생.

**원인:**
피그마 원본에서 range 구간의 흰 배경은 날짜 셀 크기를 벗어나 row 전체에 걸쳐 이어지는 구조인데,
Claude가 이 연결 레이어의 정확한 구현 방식을 파악하지 못하고 셀 단위로만 배경을 적용함.

**현재 상태:** 미수정 (결과물에 버그 존재)

---

#### 이슈 2. 연도/월 피커가 처음엔 다르게 구현됨

**증상 및 경위:**

캘린더 헤더의 "2025년 ▼" 버튼을 눌렀을 때 어떤 UI가 나와야 하는지 처음에 정확히 파악하지 못했다.

가이드 화면에는 드롭다운이 떠 있는 예시 화면이 포함돼 있었음에도,
Claude가 이를 제대로 인식하지 못하고 버튼의 눌린 상태(배경색 변경)만 파악한 채 구현에 들어갔다.
드롭다운 팝업 UI 자체는 별도 컴포넌트(Select_text)로 분리돼 있었지만,
그것과 무관하게 가이드에 있는 정보를 충분히 활용하지 못한 것이 근본 원인이다.

**1차 구현 (오류):**
버튼을 누르면 달력 전체가 연도 선택 버튼들로 교체되는 방식으로 구현됨.

**수정 과정:**
디자이너가 "가이드에는 레이어로 뜨도록 돼 있다"고 피드백 → 연도/월 피커 컴포넌트 링크를 추가로 전달 → 정확한 UI 파악 후 수정 완료.

**수정 후 동작 (올바른 스펙):**
버튼을 누르면 버튼 바로 아래에 작은 드롭다운 목록이 뜨고, 달력은 그대로 유지됨.

**교훈:**
> 버튼과 그 버튼이 여는 팝업이 피그마에서 별도 컴포넌트로 만들어진 경우,
> **두 컴포넌트의 링크를 각각 챙겨줘야** 처음부터 정확히 구현된다.
> 복잡한 인터랙션일수록 관련 링크를 여러 개 주는 게 훨씬 빠르다.

---

### 토큰(색상·폰트 값)은 어떻게 얻었나?

방법 1에서는 **별도 토큰 파일 없이도** 피그마 링크만으로 색상값과 폰트 정보를 자동으로 가져왔다.
Claude가 피그마를 읽을 때 디자인 토큰 정보(`--color/primary`, `--radius/max` 등)가 함께 포함돼 있어서, 별도로 추출할 필요가 없었다.

---

## 방법 2. Dev Mode 코드 붙여넣기

### 한 줄 요약
> 피그마 Dev Mode에서 컴포넌트별 HTML 코드를 내보내 Claude에 전달하면 Claude가 코드를 읽고 컴포넌트를 구현한다.

### 평가 결과

| 항목 | 점수 | 설명 |
|------|------|------|
| 정밀도 | ★★★★ | 색상·폰트·치수·상태 스타일이 정확한 수치로 포함되어 정적인 UI는 높은 정밀도. 단, 인터랙션 정보 없음 |
| 속도 | ★★★★ | 파일 전달 즉시 구현 시작 가능. 방법 1과 유사 |
| 준비 비용 | ★★★ | 컴포넌트별로 Dev Mode에서 직접 HTML을 내보내야 함. 여러 상태(day/period 등)를 각각 추출해야 하므로 방법 1보다 손이 많이 감 |
| 재사용성 | ★★★★ | 정적 요소는 완성도 높음. 인터랙션은 추가 작업 필요 |

### 테스트 내용: KRDS 캘린더 컴포넌트 구현

**디자이너가 한 일:** Dev Mode에서 HTML 내보내기 4개 파일 전달

| 파일 | 포함 내용 |
|------|-----------|
| `calendar-day-mode.html` | day 모드 전체 달력 (상태별 날짜 셀 포함) |
| `calendar-period-mode.html` | period 모드 전체 달력 (range 셀 구조 포함) |
| `calendar-period-select.html` | 헤더 버튼 pressed 상태 + 날짜 입력 필드 |
| `calendar-header-atomic.html` | 헤더 버튼 전체 상태 (default/hover/pressed/selected/disabled) |

**Dev Mode 파일이 제공한 정보:**
- 정확한 색상값 (`#063A74`, `#D6E0EB`, `#256EF4` 등)
- 정확한 치수 (384px 너비, 44px 셀, 32px 화살표 버튼 등)
- 날짜 셀 상태별 스타일 (day/today/on/disabled/rangeStart/rangeEnd)
- range 연결 배경 구조 — **row 뒤에 절대 위치 흰 사각형**을 깔아 셀 사이를 메우는 방식 명시
- 헤더 버튼 각 상태의 배경색

**결과물에 구현된 기능:**
- 날짜 선택 모드 (하루 / 기간)
- 이전·다음 달 이동
- 기간 선택 시 range 배경 연속적으로 연결 (방법 1의 끊김 버그 없음)
- 하단 오늘 이동 / 취소 / 선택 버튼

---

### ⚠️ 이슈: 연도/월 피커 미구현

**원인:**
Dev Mode HTML 4개 파일에는 헤더 버튼의 **시각적 상태**(default/hover/pressed/selected)만 정의되어 있다.
버튼 클릭 시 나타나는 드롭다운 패널 UI는 어떤 파일에도 포함되지 않아, 어떤 형태의 피커가 열려야 하는지 알 수 없다.

**현재 상태:** 버튼 클릭 시 pressed 상태 토글만 구현. 피커 동작 없음.

**해결하려면:** 피커 컴포넌트의 Dev Mode HTML을 별도로 추출해 함께 전달해야 한다.
이는 방법 1의 교훈(트리거-레이어 분리 구조는 레이어 컴포넌트를 따로 제공)과 동일하게 적용된다.

---

### 방법 1 레슨런 침범 기록

방법 2 구현 중 **방법 1에서 습득한 지식이 의도치 않게 사용되었다.**

| 항목 | 상황 | 처리 |
|------|------|------|
| 연도/월 드롭다운 패턴 | 방법 1에서 `Select_text` 컴포넌트 URL로 플로팅 드롭다운 패턴을 파악했고, 처음 방법 2 구현 시 해당 패턴을 그대로 사용함 | 발각 후 순수 Dev Mode 버전(`preview-devmode-pure.html`)을 별도로 제작. 레슨런 포함 버전은 `preview.html`로 보존 |

**결론:** 테스트 방법 간 지식 오염이 발생했다. 각 방법은 독립적으로 평가해야 하며, 이전 테스트 결과를 알고 있는 상태에서는 완전한 분리가 어렵다는 점도 이 테스트의 한계로 기록한다.

**출력 파일:**
- `02-devmode-code/output/preview-devmode-pure.html` — Dev Mode 파일만 사용, 피커 미구현
- `02-devmode-code/output/preview.html` — 방법 1 레슨런(드롭다운 패턴) 포함 버전

## 방법 3. 디자인 토큰 추출

디자인 토큰이란 색상, 폰트, 간격 등 디자인 시스템의 기본값들을 코드에서 쓸 수 있도록 정리한 목록이다.
예: `primary-blue = #256ef4`, `heading-font-size = 24px`

이 토큰들을 피그마에서 추출하는 방법을 두 가지 테스트했다.

---

### 왜 두 가지 방법이 필요했나?

원래는 피그마 공식 API(Variables)로 바로 가져오는 게 가장 이상적이지만,
이 기능은 **피그마 Enterprise 요금제에서만** 사용 가능하다. Pro 요금제에서는 막혀 있다.
그래서 두 가지 우회 방법을 각각 테스트했다.

---

### 3-A. 피그마 링크로 직접 긁어오기 (REST API 파싱)

#### 한 줄 요약
> 피그마 파일을 열어서 색상 칩들의 실제 색상값을 하나씩 읽어오는 방식.

#### 평가 결과

| 항목 | 점수 | 설명 |
|------|------|------|
| 정밀도 | ★★ | 전체 242개 중 106개(44%)만 추출. 색상 간 관계 정보는 완전 손실 |
| 속도 | ★★★ | 구조 탐색 + 분류 작업으로 시간 소요 |
| 준비 비용 | ★★★★ | 피그마 링크 + 접근 키만 있으면 됨 |
| 재사용성 | ★★ | 추출 자체가 불완전해 실사용 부적합 |

#### 왜 절반밖에 못 가져왔나?

피그마 파일 안에서 색상 칩들이 있는 레이어가 너무 깊이 중첩돼 있어 일부에 도달하지 못했고,
색상 이름과 실제 값의 연결 관계(예: `버튼 배경색 = primary-blue = #256ef4`)는
이 방식으로는 복원이 불가능했다.

> **결론:** 빠르지만 불완전하다. 토큰 추출 목적으로는 쓰기 어렵다.

---

### 3-B. 플러그인으로 내보내기 → Claude에 전달

#### 한 줄 요약
> 피그마 플러그인으로 토큰 정보를 파일로 저장한 뒤, 그 파일을 Claude에 전달해 코드 파일로 변환하는 방식.

#### 평가 결과

| 항목 | 점수 | 설명 |
|------|------|------|
| 정밀도 | ★★★★★ | 전체 242개 색상, 폰트 31종, 그림자 4종 완전 추출. 색상 간 관계도 보존 |
| 속도 | ★★★★ | 플러그인 실행 포함해도 수 분 이내 |
| 준비 비용 | ★★★ | 플러그인 설치 및 1회 실행 필요 |
| 재사용성 | ★★★★★ | 추출된 파일을 바로 서비스 코드에 연결 가능 |

#### 디자이너가 해야 하는 일

1. 피그마에서 Variables export 플러그인 실행
2. 저장된 JSON 파일을 Claude에 전달
3. Claude가 CSS / TypeScript 토큰 파일로 변환해줌

#### 추출된 결과

| 항목 | 수량 |
|------|------|
| 기본 색상 (primitive) | 242개 |
| 의미 색상 (semantic, 예: 버튼 배경색) | 195개 |
| PC/모바일 분기 값 | 49개 |
| 폰트 스타일 | 31종 |
| 그림자 효과 | 4종 |

#### 3-A vs 3-B 한눈에 비교

| 항목 | 3-A (링크로 긁기) | 3-B (플러그인 내보내기) |
|------|-------------------|------------------------|
| 기본 색상 | 106개 (절반 손실) | **242개 (완전)** |
| 색상 간 관계 | ❌ 손실 | ✅ 보존 |
| 폰트 스타일 | 일부만 | ✅ 31종 완전 |
| 그림자 | ❌ | ✅ 4종 |
| PC/모바일 분기 | ❌ | ✅ |
| 디자이너 준비 | 링크만 | 플러그인 1회 실행 |

> **결론:** 플러그인 실행 한 번이면 토큰 전체를 완전하게 뽑을 수 있다.
> 토큰 추출이 목적이라면 3-B가 유일한 현실적 선택지다.

---

## 방법 4. 스크린샷 전달

### 한 줄 요약
> 피그마 화면을 PNG로 캡처해서 Claude에 전달하면, Claude가 이미지를 눈으로 보고 코드를 짠다.

### 평가 결과

| 항목 | 점수 | 설명 |
|------|------|------|
| 정밀도 | ★★ | 구조·레이아웃은 파악 가능. 그러나 색상·치수·폰트 등 수치가 전부 "시각적 추정"이라 정확도 보장 안 됨 |
| 속도 | ★★★★★ | 스크린샷 캡처 후 바로 전달 가능. 별도 추출 작업 없음 |
| 준비 비용 | ★★★★★ | PNG 캡처만 하면 됨. 가장 쉬운 방법 |
| 재사용성 | ★★ | 정확한 디자인 토큰 없이 추정값으로 구현되어 실서비스 적용 전 전면 수정 필요 |

### 테스트 내용: KRDS 캘린더 컴포넌트 구현

**디자이너가 한 일:** 피그마 화면 PNG 3장 캡처해서 전달

| 파일 | 포함 내용 |
|------|-----------|
| `component.png` | 완성된 달력 전체 모습 (day 모드 + period 모드) |
| `guide.png` | 동작 가이드 (드롭다운 예시 화면 포함) |
| `atomic.png` | 날짜 셀 상태별 모음 (일요일/이벤트/비활성 등) |

**스크린샷으로 파악한 정보:**
- 전체 레이아웃 구조 (헤더/그리드/푸터)
- 날짜 셀 상태 종류 (선택/오늘/비활성/일요일/이벤트)
- 기간 선택 시 셀 모양 (시작=왼쪽 둥글, 끝=오른쪽 둥글, 중간=사각형)
- 연도/월 버튼 눌렀을 때 플로팅 드롭다운이 뜬다는 것 (guide.png에서 확인)
- 일요일·공휴일은 빨간색 (atomic.png에서 확인)
- 이벤트 날짜는 밑줄 + "이벤트" 레이블 (atomic.png에서 확인)

### 구현 오류 및 불확실 항목

#### 이슈 1. 모든 수치가 추정값 — 정밀도 보장 불가

**증상:**
색상, 셀 크기, 패딩, 폰트 크기 등 수치가 전부 시각적 추정이다.
실제 디자인 토큰과 다를 수 있으며, 픽셀 단위로 정확한 구현이 불가능하다.

**추정값 목록:**

| 항목 | 추정값 | 실제값 (Dev Mode 기준) | 오차 |
|------|--------|----------------------|------|
| 선택 셀 색상 | `#063A74` | `#063A74` | 일치 (우연) |
| 기본 버튼 색상 | `#2F74F5` | `#256EF4` | 불일치 |
| 달력 배경색 | `#EEF2F7` | `rgba(255,255,255,0)` | 불일치 |
| 셀 크기 | 42px | 44px | -2px |
| 달력 너비 | 390px | 384px | +6px |

> 정확한 수치가 필요하면 방법 1 또는 방법 2를 사용해야 한다.

---

#### 이슈 2. 연도 드롭다운 스타일 — 패턴만 파악, 세부 스타일 추정

**증상:**
guide.png에서 드롭다운이 플로팅 목록으로 뜬다는 것은 파악했지만,
목록 항목의 정확한 높이, 패딩, 선택 상태 배경색 등은 이미지로 확인이 어려워 추정으로 구현했다.

**현재 상태:** 동작은 올바르게 구현됨. 스타일 수치만 부정확.

---

#### 이슈 3. 월 드롭다운 — guide.png 미노출

**증상:**
guide.png에는 연도 드롭다운 예시만 있고 월 드롭다운은 노출되지 않았다.
연도와 동일한 패턴으로 추정 구현했으나, 원본과 다를 수 있다.

### 스크린샷으로 알 수 없었던 것들

| 항목 | 이유 |
|------|------|
| 정확한 색상 HEX 값 | 픽셀 색상 측정 불가 |
| 정확한 간격/크기 (px) | 이미지 스케일에 따라 달라짐 |
| CSS 토큰 이름 (`--color-action-secondary` 등) | 이미지에는 코드 정보 없음 |
| hover 상태 색상 | 정적 이미지라 상태 전환 확인 불가 |
| disabled 날짜 opacity 값 | 시각적으로만 추정 |

### 결론

스크린샷만으로도 **구조와 인터랙션 흐름**은 충분히 파악할 수 있다.
그러나 **디자인 시스템 토큰 수준의 정밀도**는 스크린샷으로 달성할 수 없다.
"일단 동작하는 프로토타입"이 목적이라면 빠르고 편리하지만,
실제 서비스 코드에 사용하려면 방법 1이나 방법 2로 다시 구현해야 한다.

### 추천 순서

```

   피그마 플러그인으로 색상·폰트 등 기본값 전체 추출
```
