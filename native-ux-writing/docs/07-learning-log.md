## 2026-03-11

### 케이스: 잔액 부족 오류 팝업 개선

#### 상황
토큰 전송 또는 서비스 이용 시 잔액이 부족할 때 표시되던 기존 팝업 문구를 UX 라이팅 가이드라인에 맞게 개선.

- **기존 문구:** "보유 수량이 부족하여 요청이 처리되지 않았습니다."
- **문제점:** 합쇼체 오용, 수동태("처리되지 않았습니다"), 미괄식 구조, 해결책 부재

---

#### 최종 확정안 (Version C)

| 구성 | 텍스트 |
|------|--------|
| **Title** | 잔액이 부족해요 |
| **Body** | 전송에 필요한 잔액이 부족해요. 잔액을 채운 후 다시 시도해 주세요. |
| **Button (Primary)** | 충전하기 |
| **Button (Secondary)** | 닫기 |

- **저장 위치:** `strings/08-send/texts.json`
- **Key:** `error_insufficient_balance_title` / `_body` / `_btn_primary` / `_btn_secondary`

---

#### 학습 포인트

**1. 어조는 상황의 '심각도'로 결정한다**
잔액 부족은 치명적 시스템 오류나 자산 손실 경고가 아닌 일반적인 사용성 문제다. `02-voice-and-tone.md` 기준에 따라 합쇼체가 아닌 **해요체**를 적용했다. 어미 선택은 감성이 아니라 상황의 법적 책임 여부와 심각도로 기계적으로 판단한다.

**2. 수동태는 주체를 숨긴다**
"처리되지 않았습니다"는 누가 처리하지 않았는지 책임 소재가 불분명하다. `03-writing-principle.md` 원칙 1에 따라 **능동태 동사**로 전환해 시스템이 사용자에게 명확하게 상황을 전달하도록 했다.

**3. 에러 문구는 반드시 출구(해결책)를 제공한다**
원인만 통보하면 사용자를 Dead-end에 가둔다. `03-writing-principle.md` 원칙 3(해결책 중심)에 따라 **"잔액을 채운 후 다시 시도해 주세요."** 라는 다음 행동을 Body에 명시했다.

**4. Primary 버튼은 가장 빠른 해결 경로를 가리킨다**
`04-ux-pattern-guidelines.md` 얼럿 Action 공식에 따라 제목과 버튼만 봐도 행동을 결정할 수 있어야 한다. "확인" 같은 모호한 버튼 대신 **"충전하기"** 로 명확한 다음 행동을 연결했다.

**5. 카테고리 분류 기준: 공통 vs 화면별**
오류 문구라도 발생 맥락이 특정 플로우(전송)에 한정된다면 `01-common`이 아닌 해당 화면 폴더(`08-send`)에 귀속시킨다. 공통 폴더는 화면에 무관하게 앱 전반에서 재사용되는 텍스트만 관리한다.

## Correction Logs

### 2026-03-11 — 지문 인식 실패 오류 팝업 시안 검수

#### 오류 1: 부정적 프레이밍으로 경고 문구 작성

| 항목 | 내용 |
|------|------|
| **발생 시안** | Version A, Version C |
| **잘못된 문구** | "5회 이상 실패하면 서비스가 잠겨요." |
| **위반 가이드라인** | `03-writing-principle.md` 원칙 4 (긍정적 프레이밍) |

**문제 원인**
제한 횟수 경고를 작성할 때, "잠겨요(불가)" 라는 부정적 결과에 초점을 맞췄다. 원칙 4는 시스템의 한계를 탓하는 부정어 대신 사용자가 **할 수 있는 것**을 긍정문으로 전달하도록 명시한다.

**수정 방향**
- (X) "5회 이상 실패하면 서비스가 잠겨요." → 불가능한 상황을 강조
- (O) "최대 5회까지 시도할 수 있어요." → 가능한 범위를 긍정적으로 안내

---

#### 오류 2: 일반 사용자에게 생소한 전문 용어 사용

| 항목 | 내용 |
|------|------|
| **발생 시안** | Version B, Version C |
| **잘못된 문구** | "PIN으로 인증할 수 있어요.", "PIN으로 인증해 주세요." |
| **위반 가이드라인** | `02-voice-and-tone.md` 핵심 페르소나 — 투명한 안내자 (사용자가 바로 행동할 수 있어야 함) |

**문제 원인**
"PIN"은 서비스 내부 용어로, 일반 사용자에게 낯선 기술 용어다. 사용자가 "PIN이 뭔지" 해석하는 인지 비용이 발생해 즉각적인 행동을 방해한다.

**수정 방향**
- (X) "PIN으로 인증" → 사용자에게 낯선 약어
- (O) "비밀번호로 인증" → 누구나 직관적으로 이해 가능한 일반 언어로 대체

---

#### 핵심 학습 요약

1. **경고도 긍정문으로 쓴다.** 제한·불가 상황을 안내할 때도 "할 수 없어요" 대신 "여기까지 할 수 있어요" 구조로 전환한다.
2. **전문 용어는 사용자 언어로 번역한다.** 서비스 내부에서 쓰는 용어(PIN, TX, Gas Fee 등)가 본문에 노출될 때는 일반 사용자가 즉시 이해할 수 있는 단어로 대체 여부를 반드시 검토한다.

### 2026-03-11 — 지문 인식 실패 팝업 최종 확정

#### 상황
1차 시안 3가지 검수 후 오류 교정 → Version A 구조를 베이스로 B·C의 Secondary 버튼을 보완하여 최종 확정.

#### 최종 확정안

| 구성 | 텍스트 |
|------|--------|
| **Title** | 지문 인식에 실패했어요 |
| **Body** | 등록한 손가락을 센서에 다시 올려 주세요. 최대 5회까지 시도할 수 있어요. |
| **Button (Primary)** | 다시 시도 |
| **Button (Secondary)** | 비밀번호로 인증 |

- **저장 위치:** `strings/02-auth/texts.json`
- **Key:** `error_fingerprint_fail_title` / `_body` / `_btn_primary` / `_btn_secondary`
- **os:** `android` (지문 인식은 Android 한정 용어. iOS는 별도 분기 필요)

#### 학습 포인트

**1. 단일 시안도 버튼 구성까지 완성도 있게 제안한다**
재시도 유도형 시안이라도 사용자가 반복 실패할 경우를 대비한 대안 경로(Secondary 버튼)를 함께 설계해야 Dead-end를 방지할 수 있다. 버튼 구성은 얼럿 설계의 핵심 요소이므로 초안 단계부터 Primary/Secondary를 함께 고려한다.

**2. OS 분기를 컨텍스트에 명시한다**
"지문 인식"은 Android 전용 표현이다(`01-os-guidelines.md`). `os` 필드를 `"android"`로 지정하고, iOS용 Face ID / Touch ID 버전은 별도 key로 분리해야 함을 context에 명시해 후속 작업자가 누락하지 않도록 한다.
